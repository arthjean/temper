# Temper v0.0.1

Temper v0.0.1 is an experimental Linux Cargo subcommand. Its CLI and schema-v1
report may change incompatibly during `0.x`.

## Install from source

From this repository:

```sh
cargo install --path . --locked
```

The installed executable is `cargo-temper`; Cargo exposes it as `cargo temper`.
Public crates.io publication is intentionally unavailable.

## Optimize a binary

Run Temper from a clean Git worktree containing an existing `Cargo.lock`:

```sh
cargo temper optimize \
  --package my-package \
  --bin my-binary \
  --minimum-improvement 2 \
  --timeout 300 \
  -- ./scripts/temper-workload --dataset representative
```

Everything after `--` is one workload executable followed by literal arguments.
Temper calls it directly without a shell, from the Cargo workspace root, and sets
`TEMPER_BINARY` to the canonical executable being tested. Exit status zero is the
entire correctness contract. Each invocation has its own timeout, a 1 MiB limit
for each output stream, and a dedicated Linux process group.

The workload must execute and validate `TEMPER_BINARY`. It must be representative
enough for both measurement and PGO training. `--allow-dirty` permits a dirty
worktree but records reduced source reproducibility. `--json` reserves stdout for
exactly one final schema-v1 object; progress and bounded diagnostics remain on
stderr. Human output contains no ANSI formatting when `NO_COLOR` is set.

> Trust warning: the workload and Cargo build scripts are trusted arbitrary code.
> Temper bounds execution and cleans up process groups, but it is not a sandbox
> and provides no container or untrusted-code isolation.

## Supported boundary

v0.0.1 supports only the Linux host target
`x86_64-unknown-linux-gnu`, Cargo binary targets, an existing lockfile, and
release builds made with `--locked`. Packages and executables are resolved through
Cargo metadata and compiler-artifact JSON events. Temper never edits the target
project's source, manifest, or lockfile.

The fixed search order is:

1. The project's effective release profile as the baseline.
2. Thin LTO.
3. Fat LTO with one codegen unit.
4. LLVM PGO based on the fastest stable pre-PGO strategy.

PGO uses only the `llvm-profdata` adjacent to the active rustc target-lib
directory. Missing `llvm-tools-preview` or unprovable rustflag composition rejects
only PGO.

## Measurement and decision

Screening uses two warmups and seven recorded samples per artifact. The selected
candidate is rebuilt alongside a fresh baseline in dedicated confirmation target
directories. Confirmation collects twenty paired observations in alternating
AB/BA order and applies measurement-v1.

A candidate is promoted only when every invocation succeeds, both relative median
absolute deviations are at most 10%, and the upper 95% bootstrap confidence bound
is at or below `1 - minimum_improvement`. The default minimum improvement is 2%.
A valid rejection exits successfully with `no_improvement` and promotes nothing.

## Run evidence

Every run is isolated under:

```text
.temper/runs/<run-id>/
├── run.json
├── target/
└── best/artifact        # confirmed runs only
```

`run.json` contains schema version, source state, host and toolchain fingerprint,
target identity, exact workload argv, strategy configuration and build outcomes,
raw screening and confirmation durations, checksums, rejection reasons, and the
final decision. Failed, interrupted, and no-improvement runs retain this record
once the run directory exists.

For a confirmed run, Temper copies the confirmation artifact through a synced
temporary file, preserves executable permissions, verifies its checksum, and
renames it atomically. Only after the artifact and final run record are durable
does Temper atomically replace `.temper/latest.json`.

## Explicit non-goals

v0.0.1 provides no v1 stability promise; BOLT, AutoFDO, post-link optimization,
linker replacement, Windows, macOS, musl, non-x86_64 targets, cross-compilation,
remote execution, library/example/test/benchmark optimization, compilation-time
or incremental-development optimization, Cargo dependency optimization, an
integrated build system, a Cargo fork, Cargo internal APIs, dynamic strategy
plugins, scripting APIs, daemons, services, databases, source/profile/lockfile
edits, component installation, deployment, shell-command workloads, sandboxing,
containers, untrusted-code guarantees, custom metrics, energy or memory
objectives, hardware-counter objectives, interrupted-run resume, distributed
search, cross-machine comparison, crates.io publication, and release automation
are all outside this release.
